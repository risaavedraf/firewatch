# Kubernetes deployment base

**To deploy, read and execute [`DEPLOY-GKE.md`](DEPLOY-GKE.md); this document explains why.** This is a staging deployment template for the **synthetic backend slice**, not a provisioned production environment. Compose remains the local development path. The manifests provide two replicas per service, probes, resource limits, restricted containers, disruption budgets, TLS ingress and network policies.

Everything above the last section describes what the manifests need in order to render, what the bootstrap produces and the limits measured on them. **"Path to a real production cluster"** at the end of this file is the other half: what a target cluster must bring, the cluster flavor — **decided: GKE**, registered in `odd/entrega/acta-cierre.md` §7.4 (2026-11-17) — what GKE supplies and what it refuses, the Artifact Registry and Cloud Storage shapes the provider brings, a `gcloud` provisioning checklist that has never been executed, promotion by digest, secret and CA lifecycle, the managed-data substitution with its cost and conditions, backups, rollback and what remains unverified. It changes no manifest, creates none, and none of it has been run outside a local `kind` cluster. **Nothing has been provisioned in Google Cloud**: `gcloud` is not installed on the machine this was written on, there is no project and there is no cluster, so everything below documents a target and every command in it records a step rather than an output.

## A second destination: the pitch overlay on one VM

`backend/deploy/k8s/overlays/pitch/` is a second destination for these manifests, and the only demo-only one: a single VM in `southamerica-west1` running a one-node `kind` cluster, with Caddy on the host terminating Let's Encrypt certificates in front of ingress-nginx, and the five images built on the VM and loaded onto the node by the `pitch` tag instead of pulled from a registry by digest. **It is not the production path.** Production is `overlays/delivery` applied to a real cluster, and [`DEPLOY-GKE.md`](DEPLOY-GKE.md) is what to read and execute for it; the overlay is the cheaper shape for showing the slice on a VM whose free credit does not cover a regional GKE cluster, and it differs from `overlays/delivery` in the registry, in the public identity URL and in a Caddy-to-ingress hop that is loopback and verifies no certificate.

**That overlay has not been executed on a cluster.** It was written without a cluster and without network access, so everything behind it is static: shell and Python syntax, each patch pointing at an object that exists in `base/` with the expected shape, and the realm substitution. It has not been applied and its login has not been tried, so its first run is the real test. **The document that owns that path is [`overlays/pitch/README.md`](overlays/pitch/README.md)**: start there for the VM, and go on to `overlays/pitch/CD.md` only for the automation of a run against an install that already exists.

## Configure before applying

1. Select the target cluster, registry, ingress controller and real DNS names. The five application images are pinned in `deploy/k8s/overlays/delivery`, and `deploy/k8s/overlays/delivery/pin-images.sh` does the pinning. Write the image list the cluster pulls — one line per service, `<service> <registry-path>/firewatch/<service>@sha256:<64 hex digits>`, blank lines and `#` comments allowed — and run `sh deploy/k8s/overlays/delivery/pin-images.sh images.txt`. `<registry-path>` is every segment in front of `/firewatch/<service>`: one for a registry host that serves the repository at its root, as the kind registry does, and several for one that nests it, as Artifact Registry does with `<location>-docker.pkg.dev/<project>/<repository>` ("Artifact Registry instead of a generic registry" below). The script rewrites `newName` and `digest` for every entry and fails naming the offending line when the list is malformed, repeats a service, or omits one the base declares; it is idempotent, so a second run with the same list leaves the file byte for byte identical. It is plain `awk` over two files: no `docker`, no registry access, no `yq`. The overlay is what you deploy, so the render is one command: `kubectl kustomize deploy/k8s/overlays/delivery`. A digest belongs there and not in the base: the base keeps `firewatch/<service>:replace-before-deploy` so it stays a template any clone can render before it knows its registry, while a digest names one built artifact, and writing it into the base would make that file valid for a single build and force every environment to edit the same tracked file to point at its own copy of the same commit. The digests committed here are the ones the verification cluster pulls; a different release is a different pin. The registry path is the one value the tree cannot derive — digests are content digests and travel with the image — so the committed overlay leaves that path as the single placeholder, and no other file in the repository names one.
2. Provision PostgreSQL/PostGIS and RabbitMQ with persistence, backups and TLS. This implementation uses PostgreSQL-specific SQL. Oracle production compatibility is **not** implemented. The engine itself is not open: it is PostgreSQL 17 with PostGIS 3.5, self-hosted in this cluster (`odd/entrega/acta-cierre.md` §7 and §7.3), and the managed-service substitution is documented with its cost and conditions and **not adopted** ("The data plane in the cluster, and the managed substitution not adopted" below). What an operator confirms rather than decides is their own PostgreSQL/PostGIS and broker capacity, persistence and TLS.
3. Configure an OIDC realm with RS256 access tokens, `firewatch-api` audience and `realm_access.roles` containing `viewer`/`admin`. Use Authorization Code + PKCE for a future browser client. The local password-grant client and demo accounts are not production identity configuration. **The realm is provisioned out of band, not by these manifests**: the only realm file in the repository is the development one, whose `${DEMO_ADMIN_PASSWORD}`, `${DEMO_VIEWER_PASSWORD}` and `${DIRECTORY_CLIENT_SECRET}` placeholders no Secret here supplies, so `bootstrap-secrets.sh` renders that file as the `keycloak-realm` ConfigMap and no Deployment mounts or imports it. A Keycloak that answers with no `firewatch` realm after its pod starts is therefore the expected state and not a silent failure: the realm appears when this step is done. The provider's first administrator, which is what creates it, comes from the `keycloak-bootstrap-admin` Secret in step 4.
4. Create the namespace and provision the bootstrap material with `deploy/k8s/bootstrap-secrets.sh`, or through the target secret manager using the next two tables as the key contract. The script creates every Secret in the first table except `firewatch-tls`, and every ConfigMap in the second. It never rewrites a Secret that already exists: a generated password or certificate is reused on each run, because replacing it under a running service breaks that service at its next reconnect. To rotate deliberately, delete the Secret, re-run, and restart the workloads that mount it. The ConfigMaps carry repository files and are re-applied on every run, which is safe: they are read at container start and hold no decision of their own.

| Secret | Keys |
|---|---|
| `jobs-runtime` | `DATABASE_URL` (jobs_app, TLS `sslmode=verify-full`), `AMQP_URL` (`amqps://` on 5671, user `firewatch-jobs`, vhost `firewatch`) |
| `risk-runtime` | `DATABASE_URL` (risk_app, TLS `sslmode=verify-full`), `AMQP_URL` (`amqps://` on 5671, user `firewatch-risk`, vhost `firewatch`) |
| `prevention-runtime` | `DATABASE_URL` (risk_app, TLS `sslmode=verify-full`; the frozen contract puts the `prevention` schema inside the shared risk database, so this key points at that same database and not at one of its own) |
| `postgres-credentials` | `POSTGRES_PASSWORD`, `JOBS_DB_PASSWORD`, `RISK_DB_PASSWORD`, `KEYCLOAK_DB_PASSWORD` |
| `broker-credentials` | `RABBITMQ_PASSWORD`, `RABBITMQ_JOBS_PASSWORD`, `RABBITMQ_RISK_PASSWORD`, `RABBITMQ_ERLANG_COOKIE` |
| `migration-credentials` | `JOBS_DATABASE_URL`, `RISK_DATABASE_URL` for the migration-owner Jobs (TLS `sslmode=verify-full`); never mounted by an application Deployment, because a migration owner can reshape the schema |
| `keycloak-bootstrap-admin` | `KC_BOOTSTRAP_ADMIN_USERNAME`, `KC_BOOTSTRAP_ADMIN_PASSWORD`: the identity provider's first administrator, both generated. Keycloak reads them only on a first start against an empty `identity` database; afterwards the account lives in that database and the Secret is not read again. Without an administrator no realm can be created at all, so this is the one Secret here whose value an operator has to read out of the cluster (`kubectl --namespace firewatch get secret keycloak-bootstrap-admin -o yaml`) before the realm of step 3 exists |
| `firewatch-ca` | `ca.crt` only. The signing key stays on the operator's machine (`FIREWATCH_CA_KEY`): anything able to read Secrets could otherwise mint a certificate for any service here and answer as it |

The controller renders that key as `proxy_ssl_trusted_certificate`; `tls.crt`/`tls.key` in the same Secret would be read as a client key pair this hop does not use, and a pair that does not match is rejected outright (the shape is the one ingress-nginx v1.15.1 actually read, recorded in `deploy/k8s/local/README.md`) |
| `postgres-tls`, `rabbitmq-tls`, `gateway-tls`, `jobs-tls`, `risk-tls`, `prevention-tls`, `inference-tls`, `keycloak-tls` | `tls.crt`, `tls.key`, `ca.crt`: one server certificate per service, issued by the internal CA |
| `firewatch-tls` | Ingress certificate and private key. **Not** created by `bootstrap-secrets.sh`: it certifies the public DNS name, which the repository does not own, so the operator supplies it. On a local cluster `deploy/k8s/local/ingress.sh` generates it at run time for `firewatch.example.invalid` and never commits or prints the key |

Each server certificate carries the name of the Service its clients dial (`gateway`, `jobs`, `risk`, `prevention`, `inference`, `rabbitmq`, `postgres`, and `identity` for Keycloak, whose Secret is `keycloak-tls`) as a SAN, because that is the name an in-cluster client marks when it verifies the host.

| ConfigMap | Key | Repository file it carries |
|---|---|---|
| `postgres-init` | `postgres-init.sh` | `deploy/local/postgres-init.sh`, mounted by the PostgreSQL StatefulSet |
| `rabbitmq-plugins` | `enabled_plugins` | `deploy/local/rabbitmq-plugins`, the file `RABBITMQ_ENABLED_PLUGINS_FILE` names |
| `rabbitmq-topology` | `rabbitmq-topology.sh` | `deploy/local/rabbitmq-topology.sh`, run as the `broker-provision` Job's entrypoint |
| `keycloak-realm` | `firewatch-realm.json` | `deploy/local/firewatch-realm.json`, the development realm. Rendered but **not** mounted and **not** imported, for the reason in step 3 |
| `inference-model` | `logistic.json` | `services/inference/testdata/logistic.json`, byte for byte the file the Compose stack mounts. The inference Deployment mounts the ConfigMap read-only at `/models`, so its single key lands at `/models/logistic.json` — the path `FIREWATCH_MODEL_PATH` names |

The inference artifact travels as a ConfigMap rendered by the script rather than a `configMapGenerator`, because the base's load restrictor refuses a generator file outside the kustomization root and copying the model into `base/` would give the repository two models that can drift. The volume is not `optional`: without the ConfigMap the pod stays in `CreateContainerConfigError`, and a pod whose mounted file is missing or unreadable stops at startup naming `FIREWATCH_MODEL_PATH` instead of answering from a model nobody loaded.

5. Create `jobs_app` and `risk_app` roles and separate databases. Run each corresponding application image with argument `migrate`, a migration-owner `DATABASE_URL`, and a bounded Kubernetes Job **before** deploying replicas. SQL migrations are transactional and serialized by advisory lock. PostGIS extension installation needs suitable DBA permissions. Never pass migration-owner credentials to application deployments. The prevention service shares the risk database and owns the `prevention` schema inside it: run its `migrate` Job against that same database as well, and let `009_preventive_actions.sql` create the schema and the grants of the unprivileged application role; `011_preventive_evidence.sql` adds the evidence table. Both take the next versions of the database's `schema_migrations` ledger (`009` after the risk `008`, `011` after the risk `010`), so the prevention `migrate` Job must run after the risk one.
6. Adapt `network.yaml` to your DNS, monitoring, ingress and infrastructure namespace labels; managed external databases require explicit egress IP rules. The initial port-443 egress rule is intentionally broad until the identity provider is selected. An enforcing CNI is required, and on GKE Standard that is not what a cluster has until somebody asks for it: the enforcement flag belongs to the create command and the proof to the cluster ("Provisioning with `gcloud`" below). The services no longer declare broker topology: provision the two publish exchanges (`firewatch.jobs.events`, `firewatch.risk.events`), the shared direct `firewatch.dead` exchange, the four queues (`risk.jobs.v1`, `jobs.results.v1` and their `.dead` companions) and the five bindings between them, with `deploy/local/rabbitmq-topology.sh` as the reference shape. Grant each service identity `configure` on its own exchange and queues, `write` on its own publish exchange only, and `read` on its own queue only; no service gets `write` on `firewatch.dead`, because the broker dead-letters and that grant would let one service forge a dead letter into its peer's queue. Neither identity carries a management tag, so the management API stays with an operator identity. Locally, Compose derives both service passwords from the single RabbitMQ secret it already requires, so one secret backs three identities (`firewatch`, `firewatch-jobs`, `firewatch-risk`); production needs one secret per identity.
7. Render with `kubectl kustomize deploy/k8s/overlays/delivery`, the overlay and not the base: the base alone is the template, and its `replace-before-deploy` tag names no image any cluster can pull. Then validate that render against the target cluster before applying it.

A local cluster has no metrics API, so the four HPAs of `autoscaling.yaml` read no CPU and never scale; `deploy/k8s/local/README.md` carries that half — `deploy/k8s/local/metrics-server.sh` installs the API they read, and the README records how to observe a scale-out on kind. The same directory carries the edge: `deploy/k8s/local/ingress.sh` installs the pinned controller and creates the `firewatch-tls` Secret the Ingress serves, and that README records the handshake it was measured against and the enforcement failure that proves `proxy-ssl-verify` enforces something rather than merely asserting it.

## Running the bootstrap on Windows

`bootstrap-secrets.sh` is written for a POSIX host and is what CI and any Linux operator runs. On Git Bash/MSYS it needs two workarounds, both about path translation rather than about the script's logic:

- `mktemp -d` returns a POSIX path such as `/tmp/tmp.XXXX`, which neither the mingw build of `openssl` nor the native `kubectl.exe` can open. The script then dies at the CA step **without a message**, because each `openssl` call silences its own stderr under `set -eu`. Put a `mktemp` shim first on `PATH` that prints a Windows-shaped directory (`cygpath -m "$TEMP"/...`) so both binaries agree on the same path.
- MSYS also rewrites a `-subj "/CN=..."` argument into `C:/Program Files/Git/CN=...`, which corrupts the certificate subject. `MSYS_NO_PATHCONV=1` fixes that, but it simultaneously stops the `--from-file=...=/posix/path` arguments of the ConfigMap step from resolving. The two settings cannot be active in the same run: issue the certificates with `MSYS_NO_PATHCONV=1`, then re-run with translation enabled, which skips the certificates because they already exist and lets the ConfigMaps land.

Neither issue can appear on the Linux runners this project targets, so treat them as host constraints, not defects: nothing in the manifests or the script changes for them.

## Operational boundaries

- The services never declare topology: at startup each only checks its own exchange and queues passively and fails naming the missing resource, so a missing exchange or queue is a broker provisioning fault rather than an application one. Bindings are not visible to a passive check: a missing or renamed binding stays silent at startup and surfaces later as unroutable publishes.

- OIDC issuer and JWKS endpoints must use HTTPS outside `APP_ENV=development`.
- Internal traffic between the application pods is TLS: each Deployment mounts its own `<service>-tls` Secret at `/etc/tls` and sets `TLS_CERT_FILE`, `TLS_KEY_FILE` and, where the service calls a peer, `TLS_CA_FILE`. A pod without that material refuses to start under `APP_ENV=staging` instead of serving in clear, which is the startup guard doing its job. The gateway's upstreams are `https://` and its own Service is HTTPS-only, so the ingress controller in front of it must be told the backend speaks TLS (`backend-protocol: HTTPS`, task T8) **and** that the certificate it presents must check out (`proxy-ssl-verify: 'on'` with `proxy-ssl-name: gateway` against the `gateway-upstream-ca` Secret). Encryption alone accepts any responder on that hop: the enforcement was observed by pointing the trust anchor at a CA that did not sign the gateway and reading the `502` with `upstream SSL certificate verify error: (21:unable to verify the first certificate)` in the controller log — the run is recorded in `deploy/k8s/local/README.md`. Network policies still carry the isolation, and mTLS was considered and not chosen: service identity already travels in the bearer token and, for the broker, in the AMQP user. The ingress presents no client certificate for the same reason; the gateway requires none.
- Gateway readiness reports its own availability; service readiness checks PostgreSQL. Broker loss deliberately does not remove read APIs from service: existing batches remain available and commands use the outbox.
- Quorum queues on a single local RabbitMQ node are durable, not highly available. Production needs an appropriately sized multi-node broker or a managed offering.
- A redelivered message that exhausts its five attempts is no longer left silently `queued`: the `jobs` consumer records `attempts`, `failure_reason` and `failed_at` and moves the row to `failed` (`services/jobs/migrations/004_job_failure_state.sql`), fed by the `risk.job.failed.v1` event that `risk` emits (`ReportFailure`, `services/risk/cmd/server/main.go:215`; consumed by `Fail`, `services/jobs/cmd/server/main.go:130`). An operator returns a failed or explicitly confirmed `queued` job to `queued` through `POST /v1/jobs/{id}/replay`. Dead-letter queues still need inspection for messages that cannot be decoded, and automatic replay tooling remains later work.
- Deployment replicas are not evidence of a measured availability SLA. Cluster rollout, failover, restoration, mTLS, external secret integration and load targets still require environment-specific validation.

## Path to a real production cluster

A path, documented, not a provisioning step. Three things should be separable after reading it: what these manifests already require, what an operator has to bring, and what is still a decision or still unverified. Every observation behind it comes from a local `kind` cluster (`odd/tasks/kubernetes-deployment.md` L20 and L22, `odd/tasks/k8s-delivery-closure.md` L4-L7); nothing has been applied to a target environment, and no file here changes for it. Paths are written the way this file's tree is walked: `base/` is the directory this file sits in, `deploy/` and `services/` are relative to `backend/` (the directory the commands below run from), and anything starting with `backend/`, `odd/` or `Referencias/` is relative to the repository root.

### What the target cluster must provide

**Already required by the manifests.** Pod Security Admission enforcing `restricted` in the `firewatch` namespace (`base/namespace.yaml`); an ingress controller installed as class `nginx` under the `ingress-nginx` namespace, because `gateway-entry` admits that namespace label and nothing else into the gateway; an aggregated metrics API behind `v1beta1.metrics.k8s.io`, which is what the four HPAs of `base/autoscaling.yaml` read and why they read nothing without it; and a CNI that enforces `NetworkPolicy`, because `default-deny` is an object until something acts on it. On GKE, of those three only the metrics API arrives with the cluster: GKE's own Ingress is class `gce` and not `nginx` (`base/ingress.yaml:50`, `base/network.yaml:33-36`), so the `ingress-nginx` controller is installed by the operator on either flavor; the resource metrics API is included, which removes the local recipe and not the check. NetworkPolicy enforcement, however, is **not** something a GKE Standard cluster brings on its own: on the cluster's default network the objects of `base/network.yaml` are accepted and none of them is applied, so what that file assumes is an option on the create command plus a check afterwards, not a property of the platform — a node-level question, and one of the reasons the recommendation below is Standard ("Provisioning with `gcloud`" below carries both the flag and the denied connection that accepts it). The tree pins no Kubernetes version: the APIs it uses are GA, the only version that ever admitted these pods is v1.35.0, and pinning one belongs to the decision below rather than to these manifests.

**Supplied by the operator.** A default StorageClass that can bind `ReadWriteOnce`: neither claim names a class (`base/postgres.yaml:200-207`, `base/rabbitmq.yaml:205-212`), so the cluster default is the choice, and its parameters and reclaim policy are decisions no manifest here can express. On GKE that default is `standard-rwo` ("What GKE supplies" below). A registry reachable from every **node** rather than from every pod — an image pull is the kubelet's, so no NetworkPolicy governs it, and a private registry needs its credentials in the namespace as a pull Secret; **Artifact Registry in the same project is the exception**, because the nodes' own service account is the credential ("Artifact Registry instead of a generic registry" below). The public DNS name and the `firewatch-tls` certificate of step 4, which certifies a name this repository does not own. An OIDC realm provisioned out of band, per step 3. And egress for whatever the cluster must reach outwards, which today is `dns-and-oidc`: TCP 443 to `0.0.0.0/0` for every pod in the namespace (`base/network.yaml:22-23`), a placeholder whose own comment says to narrow it in an overlay — an external identity provider and a backup Job both ride on that rule, and it is broader than either of them needs.

### Cluster flavor: decided — GKE

**The decision is taken: GKE, on Google Cloud.** It is registered in `odd/entrega/acta-cierre.md` §7.4 (2026-11-17) together with the rest of the provider amendment, and it closes what this file used to list as the only open human decision on the path. The three shapes below and the reasoning after them are kept as the ground the decision was taken on, not as an open question: these manifests are plain Kubernetes and name no provider, so what the three shapes differ in is who owns the control plane and what the money buys.

| Shape | Control plane and upgrades | What the operator still owns | Cost dimension |
| --- | --- | --- | --- |
| Managed control plane (EKS as the example) with self-managed node pools | Provider, including API availability and version upgrades | Add-ons (ingress, metrics, storage class), node pools, node and volume lifecycle | per cluster-hour + per node-hour + data transfer; **confirm at contracting** |
| Self-managed on VMs with k3s or RKE2 | You: etcd snapshots, serving certificates, API upgrades and their windows | Everything the row above lists, plus the control plane itself | per VM-hour + block-storage GB-month; **confirm at contracting** |
| Any conformant cluster the mandante already runs | Whoever runs it | Only what the two rows above require from inside the cluster | none of ours to quote; **confirm at contracting** |

No repository document gives a figure for any of the three. The one reference is the whole-scenario band of USD 1.200–1.800 monthly for the `producción empresarial` scenario (`Referencias/Actividad Dimensionamiento_FireWatch_produccion.md:143`), and `:83` states that compute sits inside that band rather than being separable from it. That band also counts a managed database, which §7.3 keeps inside the cluster instead, so it sizes the bill without quoting this shape: anything finer is a dimension with a marker, not a number.

**Why the managed control plane, and which half of the original argument survived.** The first argument stands: the control plane is the part of this system a small team cannot rehearse on demand. The second one does not — it said residency had already given up on Chile because AWS had no available region there (`odd/entrega/acta-cierre.md:155`) — and §7.4 removes it: the cluster goes to `southamerica-west1`, Santiago, so a managed control plane is no longer a concession on residency. Self-managing on VMs remains the fallback if someone must hold the hosts, and a cluster the mandante already runs remains the cheapest shape **only if** its admission, ingress class and metrics API match the list above. What is settled is the product, not the bill: GKE, with the choice inside GKE read off the table below.

**Standard or Autopilot: the choice inside GKE.** Both are the same product and both admit these manifests; what differs is how much of the node is the operator's.

| | GKE Standard | GKE Autopilot |
| --- | --- | --- |
| Nodes | You own the pools: machine types, count, lifecycle, upgrades scheduled by you | Google owns them; there is no node to reach into |
| DaemonSets and node-level agents | Allowed | Not arbitrary: the platform decides what runs next to a pod |
| Default StorageClass | `standard-rwo`, Compute Engine persistent disks, `ReadWriteOnce` | The same default |
| Resource metrics API | Included | Included |
| Ingress | Install `ingress-nginx` as class `nginx` in the `ingress-nginx` namespace | The same install, because GKE's own Ingress is class `gce` |
| What this tree asks for that the flavor forbids | Nothing | Nothing under `base/` or `overlays/` |

**Recommendation: Standard**, and the reason is a hedge rather than a manifest requirement — stated that way because the honest version is that Autopilot would admit this tree. Nothing under `base/` or `overlays/` declares a `DaemonSet`, no manifest names a `StorageClass` (the two claims leave the class to the cluster, `base/postgres.yaml:200-207`, `base/rabbitmq.yaml:205-212`) and both flavors ship the metrics pipeline, so what the manifests demand is satisfied by either. What Autopilot does not offer is the node-level surface this very file still leaves open: an egress proxy, a backup agent, or a CNI change that has to act on the `NetworkPolicy` objects of `base/network.yaml` are all node-level work, and on Autopilot there is no node to put them on. Standard keeps that surface at the price of owning node pools and their upgrades, which for two single-replica data services is not the expensive part.

**What has to be true before applying, on either flavor.** An ingress controller installed as class `nginx` under the `ingress-nginx` namespace (`base/ingress.yaml:50`, `base/network.yaml:33-36`), a default StorageClass that binds the two `ReadWriteOnce` claims, a resource metrics API answering `v1beta1.metrics.k8s.io`, without which the four HPAs of `base/autoscaling.yaml` never compute a ratio, and network policy enforcement actually acting on the objects of `base/network.yaml`, because a Standard cluster stores those policies without applying them unless the enforcement flag was part of its creation. That is the same list as "What the target cluster must provide", repeated here because it is what the choice does not change. **All of it is GKE's documented behaviour, not a measurement:** no command in this file has been run against a GKE cluster, because there is no project, no cluster and no `gcloud` on the machine that wrote it.

### What GKE supplies, and what drops out of the manual path

Two items in the local recipe are workarounds for a cluster GKE is not, and both are worth striking from the checklist rather than rediscovering on the cluster.

**The resource metrics API.** `deploy/k8s/local/metrics-server.sh` exists because a local cluster has no metrics API: it pins `metrics-server` v0.9.1 (`deploy/k8s/local/metrics-server.sh:30`) and adds `--kubelet-insecure-tls` (`:37`) because kind's kubelet certificate is not signed by the cluster CA (`deploy/k8s/local/README.md:30-32`). GKE supplies the resource metrics pipeline as part of the cluster, so the four HPAs have something to read without that script, and the insecure flag is a local concession that must not travel (`deploy/k8s/local/README.md:32`; "What differs from kind" below). What does not drop out is the assertion: that script waits for `v1beta1.metrics.k8s.io` to report `Available=True` (`:254-263`) and for `kubectl top nodes` to answer (`:293-306`), and both are worth repeating on GKE before an HPA is trusted, because a rendered manifest and an admitted pod say nothing about whether the API answers.

**The default StorageClass.** The two claims name no class and ask for `ReadWriteOnce` — 8Gi and 4Gi (`base/postgres.yaml:207`, `base/rabbitmq.yaml:212`) — so the cluster's default is the choice. On GKE that default is `standard-rwo`, backed by Compute Engine persistent disks, and `ReadWriteOnce` is what it offers, so the claims bind as they stand and no manifest changes. Two caveats, both provider knowledge rather than measurement: a cluster created before the CSI driver became the default shows `standard` instead, so the operator reads `kubectl get storageclass` before applying rather than assuming; and the disk is zonal, which is the storage the two data services have, not a high-availability claim about them.

### Artifact Registry instead of a generic registry

**The name has a shape.** An Artifact Registry Docker repository is addressed as `<location>-docker.pkg.dev/<project>/<repository>`, so on this cluster the host is `southamerica-west1-docker.pkg.dev` and an image is `<location>-docker.pkg.dev/<project>/<repository>/firewatch/<service>@sha256:<digest>`.

**How it enters `pin-images.sh`, and what the script accepts.** The script's contract is otherwise unchanged — one line per service, `<service> <registry-path>/firewatch/<service>@sha256:<64 hex>`, and it rewrites only `newName` and `digest` in `overlays/delivery/kustomization.yaml` — and `<registry-path>` carries as many segments as the registry nests. The image list line for the gateway is:


**The check, and the evidence for it.** The expression is `^([^/]+/)+firewatch/<service>$`: one or more nonempty segments, then `/firewatch/<service>`, and nothing after it. What the earlier form — `^[^/]+/firewatch/<service>$`, exactly one segment — rejected was the count of segments; the ending is what the new form still fixes, so a doubled slash, a name with no registry path (`firewatch/gateway`), and a line for `gateway` whose image ends in `/firewatch/other-service` are all rejected with the overlay left byte for byte as it was. **The nodes need permission, not a Secret.** An image pull is the kubelet's, so the credential is the node's identity: granting the cluster's node service account read access to the repository (`roles/artifactregistry.reader`) is what makes the pull work. ### Cloud Storage for the backups, with Workload Identity

**The destination changes and the policy does not.** The `pg_dump` schedule, the 30-day retention, the monthly counted restore and the RPO/RTO targets are the acta's (`odd/entrega/acta-cierre.md` §7, amended in §7.4 only in that S3 becomes Cloud Storage). Repeating the numbers here would make this file a second owner of a policy it does not own.

**Workload Identity instead of a key file.** The bucket lives in `southamerica-west1` and is written by a Google service account that holds only what writing a dump needs on that bucket. The cluster holds no key material: the backup Job's Kubernetes ServiceAccount is bound to that Google service account with `roles/iam.workloadIdentityUser`, so the pod receives short-lived credentials from the cluster's identity pool and there is no service-account JSON in a Secret to leak or rotate by hand.

**The binding is two halves, and the IAM one arrives alone only on paper.** The IAM policy binding names a Kubernetes identity: the member is `serviceAccount:<PROJECT>.svc.id.goog[firewatch/<KSA>]`. The Kubernetes side then has to ask for it, and what asks is the annotation `iam.gke.io/gcp-service-account: <GSA>@<PROJECT>.iam.gserviceaccount.com` on that ServiceAccount — the field through which the cluster's identity pool presents the Google identity to a pod running as `<KSA>`. With the IAM binding and no annotation the reservation names an identity nothing requests, and the pod falls back to the node's identity, which holds no write access to the bucket: the first upload fails and nothing before it reports the gap. The Job itself then has to run **as** that Kubernetes ServiceAccount (`serviceAccountName: <KSA>` in its pod template), which is one more reason it is a manifest this tree does not have yet ("Backups and restore" below). **The check is one upload from a pod using that ServiceAccount, before any backup is trusted**: until it happens, the annotation, the IAM binding and the bucket grant are three statements nobody has put together, and a backup policy trusted ahead of them is a schedule that writes nothing. That binding needs Workload Identity enabled on the cluster, which is why the `--workload-pool` flag is in the provisioning checklist below, and why the cluster is created with it rather than patched afterwards if the Job is ever to run. Retention is a bucket lifecycle rule rather than a delete loop inside the Job, and the monthly restore reads back from the same bucket into an isolated database: a second database, not a second cluster.

**The read side is a different identity, and its owner is T3.** Read access to the bucket that carries the data and the model artifacts is not implied by the write grant above: it is a second Google service account holding `roles/storage.objectViewer` on that bucket, bound through Workload Identity to the Kubernetes ServiceAccount of whatever reads, with the same two halves — the IAM binding and the `iam.gke.io/gcp-service-account` annotation on that ServiceAccount. No manifest here reads from a bucket today: the model artifact is the `inference-model` ConfigMap rendered from `services/inference/testdata/logistic.json` (step 4), so what is pending is the permission and a named owner rather than a workload. The owner is task T3 of `odd/tasks/gcp-gke-delivery.md`, whose scope now names the identity and the role, and `odd/tasks/plan-produccion/architecture-change-aws.md:66` points there rather than to an unnamed future step.

**The gap the provider does not close.** A backup Job's pod is not admitted to PostgreSQL at all: `postgres-entry` admits only the labels `jobs`, `risk`, `prevention`, `keycloak` and `migrate` (`base/network.yaml:196-202`), so the Job fails before Cloud Storage is involved. That is the manifest gap already reported under "Backups and restore", and moving the object store from S3 to Cloud Storage neither creates nor fills it.

### Secrets and the internal CA

`bootstrap-secrets.sh` never rotates in silence (step 4): an existing Secret is left untouched, which is what keeps a running service from losing its password at the next reconnect. Rotation is therefore always deliberate and always two halves — delete the Secret, re-run, restart the workloads that mount it — and the CA has more surface than a password.

**What a CA rotation touches.** Every `<service>-tls` certificate is signed by `firewatch-ca`, the two data services' included, and the edge anchor is a separate Secret: `gateway-upstream-ca` carries a *copy* of the CA's `ca.crt`, which is the shape and the separation `nginx.ingress.kubernetes.io/proxy-ssl-secret` reads (`base/ingress.yaml`). Both copies are guarded by the same never-rewrite rule, so a new CA does not reach the anchor by re-running the script: the anchor has to be deleted as well. If it is not, the edge **fails closed** — `502` with `upstream SSL certificate verify error: (21:unable to verify the first certificate)` — which is the measured blast radius (`odd/tasks/k8s-delivery-closure.md` L6) and the direction a failure should take.

**Order, because trust precedes identity.** A client accepts a certificate only from an authority it already has, so the new `ca.crt` has to reach every consumer of `TLS_CA_FILE` and of `sslrootcert=/etc/tls/ca.crt` before any server presents a certificate from it; in practice that is a restart of the clients first, and the two copies of the anchor make it two steps rather than one. **That order is necessary and not sufficient: during the transition the bundle has to carry both roots.** A client holding only the new root rejects a server still presenting a certificate from the old one, and a client still on the old root rejects the first server re-issued under the new one, so swapping one anchor for the other breaks the connections it moves in both directions. `ca.crt` therefore becomes a multi-certificate PEM holding old and new, on every consumer of `TLS_CA_FILE` and of `sslrootcert` and in the edge anchor `gateway-upstream-ca`; the cut to new-only is a later step, taken once every server certificate has been re-issued and its handshake verified. `bootstrap-secrets.sh` writes one `ca.crt` per Secret, so overlapping means concatenating both roots before that Secret is re-created; where the material at hand does not allow it, this is a coordinated maintenance window with downtime, not a hot rotation. Only the fail-closed direction is measured — the `502` with `upstream SSL certificate verify error: (21:unable to verify the first certificate)` described above — and the overlapping order itself is what the material requires, not an observation: it has not been rehearsed on any cluster.

**Two traps worth naming.** Issuing any certificate needs the CA signing key on the machine that runs the script (`FIREWATCH_CA_KEY`, default `~/.firewatch-internal-ca/ca.key`), because the cluster deliberately does not hold it. Without that key the script says so on stderr, keeps the existing certificates, and a Secret deleted for rotation simply stays absent, so the workload mounting it never starts — visible, but late. And deleting `firewatch-ca` itself is a CA *replacement*, not a rotation: the script mints a new CA and overwrites the local key while every `<service>-tls` still chains to the old one, so the two have to be deleted and re-issued together.

The realm is the other piece that does not live in these manifests: provisioned out of band (step 3), with the only realm file in the tree being the development one, so a Keycloak answering with no `firewatch` realm is the expected state rather than a silent failure.

### The data plane in the cluster, and the managed substitution not adopted

PostgreSQL/PostGIS and RabbitMQ are StatefulSets of **one replica each** (`base/postgres.yaml:53`, `base/rabbitmq.yaml:101`) with `ReadWriteOnce` claims, so their availability is the node's availability and a quorum queue on one node is durable, not highly available — the note under "Operational boundaries" already says that, and it is the honest starting point for the comparison below.

**What managing them would buy.** Platform backups with a restore path somebody else tests, HA and automated failover, minor-version maintenance, and a smaller operator surface. One of those exceeds the agreed objective rather than meeting it: the policy in `odd/entrega/acta-cierre.md:189-192` deliberately does not promise point-in-time recovery, so a managed PITR window would be more than the RPO of 15 minutes requires.

**What it would cost, in the code and in the manifests, because that is the real price.** (1) Egress: a managed endpoint sits outside the cluster, and `default-deny` means every consumer needs an explicit rule to it — step 6 already says managed databases need explicit egress IP rules, and 443-to-anywhere is no substitute for 5432 or 5671 with TLS inside. (2) `bootstrap-secrets.sh`: `postgres-credentials`, `postgres-tls` and `rabbitmq-tls` become provider-issued material, `postgres-init` stops creating roles, databases and extensions, and the broker accounts come from the offering. (3) Migration ledger: the runner applies each version inside one transaction under `pg_advisory_xact_lock(1)` (`backend/services/risk/cmd/server/main.go:70`, `:94-102`), and `prevention` creates its schema and grants inside the shared risk database (step 5), so the offering must allow `CREATE EXTENSION postgis`, transactional DDL, advisory locks and schema grants — a provider that forbids any of them breaks the ledger, not just the deploy. (4) TLS: the runtime DSNs say `sslmode=verify-full&sslrootcert=/etc/tls/ca.crt` against certificates whose SAN is the Service name, and a managed endpoint has a different name and a different authority, so those Secrets and the path they name both stop being valid. (5) Policy: `postgres-entry` and `rabbitmq-entry` become dead objects and the egress side grows. (6) Broker least privilege: the two identities with per-exchange and per-queue grants (step 6, `V1-H-04`) must be expressible by the offering; one that only grants per vhost breaks the matrix. (7) Backups: managed retention has to be checked against a 15-minute RPO, and a coarse granularity still leaves the logical dumps in place.

**Cost, with the dimension named.** The band above already counts a managed database, so adopting one adds no quotable figure to this repository — it moves what sits inside a band the mandante has already read. Priced properly it is per vCPU-hour plus storage GB-month plus backup GB-month for PostgreSQL, per instance-hour for a managed broker, and data transfer between cluster and provider when they are not colocated: **confirm at contracting**, for each.

**Not adopted.** The data plane stays inside the cluster, decided in `odd/entrega/acta-cierre.md:161-175` (§7.3) and owned by front 14 (`odd/plan-produccion/14-motor-datos-continuidad.md`); the substitution is documented with its cost and its conditions, and it is not the current design.

### Rollback

**Rolling a Deployment back is rolling the overlay back**: the previous digest list goes through `pin-images.sh`, the render is reviewed, and `kubectl apply -k` moves the pods onto it. `kubectl rollout undo` is not the mechanism here, because it edits the Deployment and the next `apply -k` of the overlay would overwrite that edit; editing the `base` is never the mechanism, since a digest there would make the template valid for one build. The precondition is that the previous digest is still in the registry: retention and tag immutability are part of rollback, not housekeeping.

**What cannot be rolled back is the schema.** The runner applies the versions the code carries and records them (`backend/services/risk/cmd/server/main.go:94-102`), there is no down path, and a version recorded in a deployed ledger can never be renumbered or moved (`backend/docs/migration-ledger.md:30-32`). A rollback that crosses a migration is therefore a restore, not a rollback: the older image would run against a schema it does not know. Rolling forward with a fixed image is the only reversible direction, and the overlay is what makes that a one-file change.

**Two declared gaps make roll-forward-with-replay non-atomic.** (1) A failure event in flight before a replay still matches the re-queued row: `Fail` transitions only a `queued` row (`backend/services/jobs/internal/repository/store.go:206-209`), and a replay returns the row to exactly that state, so a late failure can terminate a job that was just re-dispatched — the guard protects a terminal row, which is the boundary `odd/tasks/security/backend-hardening/07-job-recovery.md:60` declares. (2) A batch persisted in `risk` whose completion never arrived is recovered only by an operator's attested re-dispatch, which re-emits the stored batch's completion; duplicate work is bounded but not prevented (`backend/docs/operations.md:193-200`, `:209-214`). Both are declared limits of the recovery policy, and neither is hidden by a rollback.

- The Windows workarounds ("Running the bootstrap on Windows" above) exist because Git Bash, mingw's `openssl` and a native `kubectl.exe` disagree about paths. On a Linux host or CI runner they do not apply, and nothing in the manifests depends on them.
- The `proxy-ssl-secret` key shape — `ca.crt` alone — was determined against ingress-nginx `controller-v1.15.1` (`deploy/k8s/local/README.md`). A different controller version is a new measurement, and the failure mode is not a partial hop: an annotation the controller rejects removes the whole `ProxySSL` block, so the hop stays encrypted and unverified with nothing saying so (`odd/tasks/k8s-delivery-closure.md` L6).
- A cold cluster starts the Jobs before PostgreSQL and RabbitMQ answer. On kind `broker-provision` failed once and `migrate-v14` three times, and both completed by retry (`odd/tasks/k8s-delivery-closure.md` L4); a real cluster's first volume attach is slower, so the same race should be expected and no manifest orders it.
- `kubectl wait --for=condition=Ready pod --all` is not an acceptance criterion in a namespace with Jobs: a finished Job's pod stays `Ready=False` forever and the command fails on a healthy rollout (`odd/tasks/k8s-delivery-closure.md` L4). Read per workload.
- `metrics-server --kubelet-insecure-tls` is a local concession (`deploy/k8s/local/README.md`), never a production setting: GKE brings its own resource metrics pipeline, so neither the recipe nor the flag travels.
- The StorageClass. kind supplies a default local-path provisioner; on GKE the default is `standard-rwo`, and on any other cluster it is the operator's. No manifest here names one, which is what keeps this choice out of the tree.
